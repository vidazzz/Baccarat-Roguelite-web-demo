# 《澳门风云》MVP 技术设计文档

## 1. 技术目标

MVP 的技术目标是快速、可重复地验证核心玩法，并优先保证 3D 搓牌的操作质量。系统需要支持两座赌场、多张后台同步运行的牌桌、标准百家乐规则、可配置的概率改写、图形化路单和轻量餐厅经营。

当前不追求完整商业化架构。设计应保持模块边界清晰，使规则、概率和经济数值可以快速修改，并为未来迁移桌面打包或其他引擎保留空间。

## 2. 技术选型

| 领域 | 选择 | 原因 |
| --- | --- | --- |
| 语言 | TypeScript | 为规则、状态和配置提供类型约束 |
| 构建工具 | Vite | 启动快、热更新快，适合原型迭代 |
| 2D 界面 | HTML + CSS | 适合高密度路单、牌桌选择和经营界面 |
| 3D 搓牌 | Three.js | 直接控制网格、材质、镜头和指针交互 |
| 动画 | 原生 `requestAnimationFrame`、CSS Transition | 管理发牌、镜头、揭牌和昼夜淡入淡出；避免额外运行时依赖 |
| 音频 | 暂无外部音频依赖 | 当前 MVP 先验证视觉、输入和规则反馈 |
| 状态管理 | `Game` 领域状态 + `main.ts` 流程状态 | 当前单机规模足够，保持界面与规则边界清晰 |
| 单元测试 | Vitest | 验证百家乐规则、路单、概率和经济系统 |
| 端到端测试 | 浏览器手测 / 可按需接入 Playwright | 验证选赌场、选桌、下注、搓牌和结算流程 |

当前实现不引入 React；2D 界面由模板字符串和 DOM 事件驱动，Three.js 搓牌场景直接封装在 `TableScene` 中，避免把高频网格更新放入 UI 渲染生命周期。

## 4. 页面与运行状态

当前页面状态：

```text
MAP
RESTAURANT
SKILLS
CASINO_SELECT
LOBBY
TABLE
DEALING
GAME_OVER
```

`MAP` 是首屏和地点切换入口；`RESTAURANT`、`CASINO_SELECT / LOBBY / TABLE / DEALING` 和 `SKILLS` 是功能场景。`activeActivity` 与当前视图分开保存：返回地图只改变视图，只有从地图进入另一地点才改变实际活动和时间规则。

牌桌内部使用显式状态机：

```text
TABLE(BETTING)
  -> DEALING(animating / drawing-card)
  -> DEALING(awaiting-card / dealer-revealing)
  -> DEALING(settling-chips)
  -> DEALING(settled)
  -> TABLE(BETTING)
```

状态转换必须由领域事件驱动，避免由动画回调直接修改资金或开奖结果。动画完成后只发送“表现已完成”事件，由状态机决定下一步。

## 6. 核心数据模型

当前连战和筹码账本使用以下领域状态：

```ts
interface PendingChain {
  tableId: string;
  stake: number;             // 现金等价值，实际由筹码锁定
  plannedRounds: number;
  legs: { index: number; target: Outcome; result: BaccaratResult }[];
}

interface GameWallet {
  cash: number;
  chips: number;
}
```

连战确认时一次性扣除 `stake / 100` 枚可用筹码；每条 leg 只保存独立目标。结算统计和局并从指数 `K` 中排除，成功返还 `stake * 2 ** K` 现金，失败不返还。

下注草稿由表现层维护连续目标数组：初始只渲染一行，选中第 `i` 行后自动追加第 `i + 1` 行，最多达到牌桌 `maxChainRounds`。同一目标再次点击时，仅当它位于最后一个已选目标才允许撤销，并同步裁剪后续空白行；取消操作清空整个草稿。筹码数量由单一滑块决定，确认时所有 leg 使用同一 `stake`。

表现层为连战创建 N 个独立的 `TableScene` 容器。横屏使用 `repeat(N, minmax(0, 1fr))` 等分为单行并排布局，并随列宽压缩牌桌与播报；竖屏回退为单列以维持可操作面积。每个 leg 保存自己的发牌数量、公开牌集合、透视牌集合和神助状态，动画与输入互不打断。已结算 leg 禁用正常翻牌，但千术目标选择仍可覆盖该限制；牌桌按精确命中、和局或未命中显示对应徽章。领域状态按 leg 独立结算，结算后的 `RoundResult` 仍以引用保留在本场链和牌路历史中。

千术目标选择不使用“当前牌局”作为领域前提。UI 在启动任意千术、选择指定边数和确认调换前先检查 `CHEAT_SKILL_COST`；余额不足时保留技能按钮可点击以显示费用提示，但不得进入目标选择或修改牌序。规则层仍通过 `consumeChips()` 做最终原子校验。通过费用检查后，UI 为所有 `TableScene` 标出合法目标，已结算牌局也包含在内；点击任意目标时将 `chainLegIndex` 传入规则层，只更新目标 leg 的牌序与该场景。指定边数是两阶段操作：先保存任意盖牌目标，随后在现有千术面板中选择牌型，并调用 `Game.useSetEdge()` 在验证成功后随机替换为该类型的一张牌及扣除 1 枚筹码。放弃按钮是全局操作，调用 `abandonPendingRound()` 结束整场连战。

`Game.reconcileChainAfterCheat(legIndex)` 用于改牌后重算已结算 leg。该方法不重复追加牌路历史，也不重复支付赔付：若所有 leg 精确命中各自目标，则立即完成连战；若还有败局或非目标和局且仍有筹码与合法千术目标，则保留 `PendingChain`；资源耗尽或 UI 判定已无合法目标时，通过 `finalizeSettledChain()` 完成最终结算。重算已结算 leg 不会清除另一个仍在进行的 `pending` 上下文。

`TableScene` 使用俯视基准相机。当前玩家点击己方牌与荷官牌都调用 `revealFocusedByDealer()`，聚焦后自动翻牌；若触发神助，则统一进入 `beginDealerDivineReveal()`。咪牌底层实现暂时保留但不从正常翻牌入口调用，便于后续恢复。透视盖牌以独立 `peekMask` 覆盖蓝色半透明遮罩，`revealed` 状态仍为 `false`；自动翻牌或神助开始前恢复牌背并隐藏遮罩，因此透视不改变发牌、计分、补牌或结算状态。

## 7. 多赌场与多桌调度

### 7.1 运行原则

- MVP 两座赌场的所有牌桌均存在于数据层。
- 只有当前进入的牌桌创建 Three.js 场景。
- 后台牌桌无需按帧运行，只需根据逻辑时间推进状态。
- 从其他页面返回大厅时，应根据已过去的逻辑周期补算结果。

### 7.2 调度方式

牌桌调度器维护统一逻辑时钟。每张桌记录阶段结束时间，应用以低频定时器或页面事件检查到期桌并推进状态，而非为每张桌建立高频循环。

为保证可测试性，调度器应支持：

- 实时时钟；
- 测试用手动时钟；
- 暂停与倍速；
- 固定随机种子；
- 一次推进指定牌局数。

浏览器页面失去焦点时，定时器可能被节流，因此恢复焦点后必须按照时间戳补算，不能依赖定时器被准时调用。

## 8. 结果生成与概率改写

### 8.1 解析顺序

```text
读取桌面历史
  -> 识别当前路势
  -> 获取基础结果分布
  -> 应用世界路势偏移
  -> 归一化并限制上下界
  -> 使用种子 RNG 抽取目标结果
  -> 生成符合目标结果与百家乐规则的有效牌序
  -> 按发牌阶段逐张揭示
  -> 阶段最后一张牌检查信心与神助
  -> 第一阶段选择牌型并从短边连点挤牌
  -> 必要时第二阶段选择吸/吹并从长边连点挤牌
  -> 在不改变补牌结构的合法候选中改写当前暗牌
  -> 重新计算结果并继续揭示
```

### 8.2 重要约束

1. 普通搓牌轨迹不改变结果；只有显式触发的神助小游戏可以改写当前阶段最后一张暗牌。
2. 所有修正器必须提供来源、触发条件、修正值和应用前后分布，供调试面板检查。
3. 最终分布需要统一归一化，并设置可配置上下界，防止技能叠加产生必胜。
4. 随机过程必须可通过种子复现。
5. 生成的具体牌局必须满足百家乐第三张牌规则，不能只伪造最终点数。
6. 神助改牌不得改变已经确定的补牌张数，也不得修改任何已公开牌。
7. 实时判势函数只接收已公开的庄闲牌值、当前牌位和一个假设点值；返回立即结算、闲补牌、庄补牌或仍待定，不得读取预生成暗牌。

### 8.3 信心结算

信心在 `Game.play()` 确认下注后一次性结算，UI 在封盘前不得调用预览公式。计算式为：

```text
confidence = clamp(
  0%
  + floor(下注额 / 封盘前流动现金 / 10%) * 5%
  + 同向标记路数数 * 5%
  + Σ max(0, 同向标记路数长度 - 1) * 2%
  - 反向有效路数数 * 5%
  + 当前局连胜数 * 1%
  + 前序盈利日连胜数 * 5%,
  0%, 100%
)
```

- 牌桌保留单调递增的 `historyOffset`。珠盘路格位使用 `historyOffset + localIndex` 计算，历史裁剪后仍能继续向后落格；渲染层只显示最新九列并自然左移。
- 珠盘路点击后无条件写入整盘标记。珠盘路专属识别器以 `history.length` 对应的下一格为基准，从同一行按索引步长 6 向左回溯；连续 4 个同侧结果构成金刚路，交替结果用于珠盘路单跳判定。识别为空不能删除标记。
- 除珠盘路专属的下一格规则外，其他识别器必须以最后一局为后缀终点；固定节奏类大路允许跳过无关前缀，但不得命中已在更早位置结束的旧图形。大路标记记录起始显示列和对应历史局索引；只有点击列产生的路型在类型、预测方向和长度上都与完整路书的当前有效后缀一致时，标记才生效。
- 每个下三路格子保存生成它的原始 `roundIndex`。点击大眼仔路、小路或曱甴路时，以点击列为起点过滤对应红蓝格子，并将该列至末列写入独立 `RoadMark`；其生效条件同样要求点击列精确等于当前有效后缀的起始列。
- 下三路识别器对过滤后的红蓝序列应用通用路型规则。预测颜色分别与 `predictRoadColors(history, "banker")` 和 `predictRoadColors(history, "player")` 比较；只有恰好一侧会生成预测颜色时，才输出庄或闲预测并进入信心公式。
- 反向惩罚读取当前完整历史中的全部有效路数，不受标记影响。
- 每份路书的识别结果必须先经过唯一分类：路书专属型优先，其次依次为长路、单跳、逢某方连/不连、不长过 N 口；同一路书最多返回一个 `ConfidenceRoadPattern`。不同路书之间按 `source + id` 去重并允许叠加。
- 标记状态与识别结果分开存储。正常 UI 的点击反馈只确认标记已记录，不得根据识别成功或失败改变颜色、文案或动画；当前测试构建可以保留带 `DEBUG` 前缀的识别详情。
- 信心仅传给神助触发抽样，不得传入神助两阶段命中率或结果改写强度。
- 下注占比使用封盘扣款前的流动现金，暂不包含餐厅估值；每日盈利按已结算赌局净收益记录。
- 调试滑块只修改基础信心，100% 锁定为独立开关；信心只进入 `shouldTriggerDivineAssist()`，不得修改两阶段各自的固定命中率。
- 创造路数保存为每桌独立的庄闲序列。任一路书上的合法下一格操作都要投影为同一庄闲结果并同步渲染到其余路书；修改序列中的较早位置必须截断后续项。结算只消费首个预测，首项失败时清空整段并立即扣除信心。

### 8.4 牌序生成策略

概率系统决定“庄、闲、和”目标结果后，牌局生成器需要产生与之相符的合法牌张。MVP 可采用以下方式之一：

- 从真实牌靴反复抽样，直到得到目标结果；
- 预先枚举或构建合法牌型组合，再按目标结果采样；
- 使用条件采样算法，在保留牌靴约束的情况下生成目标结果。

建议原型先使用带最大尝试次数的条件抽样，并记录失败回退。若未来需要严格模拟有限牌靴、算牌或烧牌，则需要升级为真正的条件牌靴模型。

## 9. 路单实现

### 9.1 数据与渲染分离

珠盘路和大路生成器接收标准化历史结果，输出格位数据：

```ts
interface RoadCell {
  row: number;
  column: number;
  outcome: RoundOutcome;
  ties: number;
  bankerPair?: boolean;
  playerPair?: boolean;
}
```

UI 只根据格位数据绘制圆点、颜色和附加标记。大厅压缩版与牌桌完整版共享同一份路单结果，仅使用不同尺寸和裁剪范围。

牌桌完整版把珠盘路、大路、大眼仔路、小路与曱甴路分区排列，并保留牌局统计；问路栏当前不渲染。图标由 CSS 根据路型绘制，大眼仔路为空心圆、小路为实心圆、曱甴路为斜杠。大路和局保留在上一枚庄或闲格位的 `ties` 字段中，渲染为绿色斜杠，`ties > 1` 时额外显示次数。赌场大厅每张牌桌独占一行，复用同一套路纸生成与渲染函数，只缩小格子尺寸和可见列数。

### 9.2 渲染技术

MVP 优先使用 CSS Grid 或 Canvas：

- CSS Grid 更利于无障碍、调试和快速调整；
- Canvas 更适合大量小格和高频缩放；
- 当前单桌历史规模较小时，CSS Grid 足够。

不使用文字序列替代正式路单。颜色之外应保留形状或标记差异，以降低色觉识别问题。

### 9.3 牌桌下注布局与暂存账本

牌桌页使用纵向一体布局：绿色牌桌和三个落注区位于上方，操作按钮与筹码托盘压在桌沿下方，完整路单紧随其后。路单继续使用 DOM 与 CSS Grid，不进入 Three.js 场景。

下注使用两阶段筹码事务：

```text
选择筹码
  -> 点击下注区
  -> 立即从 chips 扣款并累计到 reservedChipWager
  -> 可继续叠加同面额或切换筹码面额
  -> 取消：reservedChipWager 全额返还 chips
  -> 确认：reservedChipWager 清零并转成 PendingRound.bet，不再次扣款
```

- `reserveChipBet()` / `reserveBetChip()` 只接受正数、筹码余额足够且当前没有待结算牌局的请求。
- `cancelReservedBet()` 只能返还内部记录的暂存总额，不能接受外部退款金额。
- `play()` 在存在暂存筹码时要求确认金额完全一致，避免少扣、多扣或重复扣款。
- 旁观或离开牌桌前必须自动取消暂存筹码。
- 当前单轮只允许一个下注区域；多区域下注需要先重新定义玩家拿牌归属和神助目标，不在本次范围内。

旁观使用独立的二维表现状态机，不创建 `TableScene`：

```text
生成合法牌局
  -> CSS 位移动画依次发初始四张
  -> CSS 翻面动画逐张公开初始牌
  -> 若闲补牌：发闲第三张并翻开
  -> 若庄补牌：发庄第三张并翻开
  -> Game.settle()
  -> 原牌桌显示结算覆盖层并刷新下方路单
```

二维牌面复用标准扑克角标、花色点阵和人头牌 DOM 结构。动画只改变牌元素的位移和 `rotateY`，不创建 WebGL 渲染器、不切换页面，也不执行摄像机运镜。正式下注后的开牌仍使用 Three.js 流程。

## 10. 3D 搓牌实现

### 10.1 场景范围

Three.js 场景只负责：

- 桌面局部；
- 当前牌局纸牌；
- 基础发牌动画；
- 关键牌近景；
- 搓牌变形和揭牌反馈。

MVP 不制作完整赌场空间、荷官模型或真实手部动画。

3D 桌面不渲染押注区或牌靴模型，只渲染上下分布的庄闲发牌放牌区。玩家下注的一方固定在近侧，对家固定在远侧，初始四张及补牌直接从场景上方移动到所属牌位，不再执行下注方二次推牌。每张牌保存桌内牌位 `tableTarget` 和稳定牌位 `target`；场景因应用状态刷新而重建时，已发出的牌直接恢复到稳定牌位，避免跳回发牌点。

默认相机根据 Canvas 宽高比调整回桌距离，窄屏自动后退以保持双方牌位完整。单牌聚焦时，相机位置与观察点使用相同的横向和纵深位移，从玩家侧直接向目标牌推进，避免围绕牌桌旋转产生大角度转向。

### 10.2 纸牌模型

纸牌使用细分平面或极薄几何体：

- 正反面使用独立材质或双面着色；
- 网格拥有足够顶点，以支持局部弯曲；
- 顶点变形依据抓取角、拖动向量和距离计算；
- 通过限制函数保证纸牌不会异常穿折；
- 松手时用阻尼插值回弹，越过阈值则进入完整揭牌动画。

不引入完整软体物理引擎。可控网格变形更容易保证输入与视觉结果稳定对应。

### 10.3 输入流程

1. 将指针射线投影到牌面平面；允许交点位于牌面几何范围之外。
2. 将按下位置转换为镜头相对角度，并吸附到长边、左下角或短边三个固定法向量之一。
3. 按下后锁定法向量，只使用后续位移在该法向量上的投影计算揭露进度。
4. 更新网格顶点、阴影、音频参数和镜头细微反馈。
5. 达到完成阈值时立即进入完整揭牌；未达到时松手必定回弹到零进度，并可重新吸附方向。
6. 完成阈值为总推进距离的 70%。进入咪牌镜头时遮挡物保持隐藏；指针按下后立即生成在牌角，第一次推进起便附着翻折面运动，保证数字和花色不会提前露出。未完成回弹结束后清空遮挡几何体，下一次按下重新生成。
7. 将指针增量同时投影到折线法向和切向：法向负责开牌推进，切向负责移开手指。切向连续意图达到阈值且显著占优后才锁定移手模式；移手期间冻结开牌进度，明确的法向推进可切回开牌模式。
8. 未完成松手时，牌面推进量和手指移开量一并回弹至零。
9. 完全揭牌后向应用状态机发送表现完成事件。

需要同时支持 Pointer Events，以便未来扩展触控，但 MVP 以鼠标体验为验收基准。

### 10.4 3D 筹码与结算移交

- 确认下注时保存每枚筹码的 `value` 和 `colorIndex`，发牌场景建立后在下注方对应位置重建筹码堆。
- 筹码圆柱体颜色和顶部贴图必须与下注托盘面额对应；赔付金额使用当前赌场面额从大到小精确拆分。当前不启用庄家抽水，也不需要抽水余数筹码。
- 赢局保留原下注筹码，并把赔付筹码从荷官侧移动到下注位置；输局把原筹码从下注位置收回荷官侧；和局把原筹码退到玩家侧。
- `SETTLING_CHIPS` 是独立表现阶段，移交完成回调只推进流程状态，不重复修改资金。资金仍由 `Game.settle()`唯一结算。
- `TableScene.dispose()` 必须释放筹码几何体、材质、动态 Canvas 纹理和动画引用。

### 10.5 性能目标

- 桌面目标帧率：60 FPS；
- 指针移动到画面反馈尽量控制在一帧内；
- 拖动期间不得触发 UI 框架的全局重渲染；
- 纸牌纹理应预加载；
- 当前桌离开后正确释放几何体、材质、纹理引用和事件监听。

## 11. 餐厅与经济系统

当前经济规则只有一种筹码：现金不直接购买筹码，餐厅周期和餐厅抵押产出筹码，所有赌场门票、下注、暂存和出千消耗筹码；赌场赢钱返还现金，取消暂存、和局退款和出千失败退款返还筹码。餐厅抵押通过 `pawnDebtCash` 记录累计债务并允许重复抵押，赎回金额为债务的 2.5 倍。牌桌保存 `dealerCash` 与 `dealerRewardClaimed`，荷官资金初始并每日重置为 `¥10,000`，当天抵押奖励只触发一次。

餐厅配置与状态分离：

```ts
interface RestaurantLevelConfig {
  level: number;
  upgradeCost: number;
  incomePerCycle: number;
  pawnValue: number;
}
```

应用维护独立的游戏世界分钟轴，与现实毫秒计时分离：

- 赌场外采用 `60 游戏分钟 / 现实秒`；
- 赌场内采用 `1 游戏分钟 / 现实秒`；
- 游戏日按 24 小时循环，时钟跨过 24:00 时递增天数；
- 牌桌大厅轮次、动画和小游戏继续使用现实毫秒，不读取世界时间；
- 牌桌进入玩家输入或确认状态时，将世界时间增量设为零；现实毫秒循环和其他桌的即时结算继续运行；
- 自宅、已打烊餐厅、日程弹窗、休息过渡和玩家确认状态都把世界时间增量设为零；
- `activeActivity` 与视图状态分离，地图视图继承玩家离开前地点的时间规则；
- `tickRealtime()`在一个现实帧可能跨过关键时点时，只推进到最近事件边界并返回 `restaurantClosingReached`、`sleepDeprivationStarted` 或 `sleepDeprivationCollapseReached`，由 UI 显示反馈后再继续。

单机实时循环每累计 60 游戏分钟餐厅经营时间后：

- 只有 `restaurant.open && !restaurant.pawned && !insideCasino` 的分钟数计入经营周期；
- 正常营业窗口为 08:00 至 20:00。玩家身处餐厅时，时钟在 `closeAtWorldMinute` 精确暂停并弹出打烊选择；身处其他活动时自动关闭；
- 继续营业把 `open` 设为 `true`，并把 `closeAtWorldMinute`推进到最近的下一次 20:00；打烊状态进入餐厅后保持暂停，直到继续营业或切换地点；
- 进入赌场、餐厅打烊或典当时冻结已有周期余量，不重复发放收益。

疲劳在领域层以世界分钟为单位记录，但玩家界面只显示模糊困倦文案：

- 每跨过 00:00，`sleepDebtWorldMinutes += 480`；休息按每分钟一比一扣减，并允许跨多个午夜继续计算；
- `restUntilNaturalWake()`在内部量低于 60 分钟时拒绝执行，否则计算包含途中新增量的最早清零时刻；
- `restUntilNextOpening()`固定跳到下一日 08:00，保留未清除部分；
- 睡眠不足惩罚流程暂未启用；睡眠债务仍按世界分钟累计并可通过休息清除，启用后再安排 08:00 检查与晕倒事件；
- `lastSleepDurationWorldMinutes`用于醒来提示，玩家文案不得出现内部变量名称或“睡眠债务”术语。

地图和自宅昼夜资源各自同时预载两张同尺寸图片。容器以 `daylight/night` 类切换透明度，CSS 使用 1.5 秒交叉渐变；当前昼间边界为 06:00 至 18:00。

当前资金直接由 `Game` 修改。若后续增加存档和复杂经济事件，建议统一迁移到以下账本接口：

```ts
interface LedgerEntry {
  id: string;
  type: "bet" | "payout" | "restaurant_upgrade" | "restaurant_income" | "pawn";
  amount: number;
  balanceAfter: number;
  createdAt: number;
  referenceId?: string;
}
```

统一账本将便于排查重复结算、负余额和经济参数问题。

## 12. 配置与调试工具

以下内容不得硬编码在 UI 组件中：

- 赌场数量、桌数、单次门票和下注上下限；
- 阶段时长；
- 路势触发条件和概率偏移；
- 路数识别阈值、长度规则和信心修正值；
- 概率上下界；
- 餐厅升级成本、周期收益和典当价格；
- 餐厅营业时间、午夜疲劳增量、自然醒最低门槛和晕倒阈值；
- 昼夜边界和背景交叉渐变时长；
- 初始资金和赔率。

调试面板至少提供：

- 当前随机种子；
- 所有牌桌的阶段、历史和下一次推进时间；
- 当前路势识别结果；
- 基础、路势修正后的牌局概率，以及封盘信心分项；
- 已冻结的目标结果和具体牌序；
- 暂停、倍速和立即推进牌局；
- 修改现金、餐厅等级和技能等级；
- 调整基础信心，并独立锁定 100% 信心；
- 导出最近若干局调试日志。

生产构建应能关闭调试入口。

## 13. 测试策略

### 13.1 单元测试

必须覆盖：

- A 至 K 的百家乐点数换算；
- 自然牌、第三张牌和庄闲补牌规则；
- 基于公开牌的逐点值结果预测，覆盖天生牌、闲补、庄补和最终胜负；
- 庄、闲、和结果判断；
- 珠盘路和大路的典型排列与边界情况；
- 通用、珠盘路专属和大路专属路数识别及长度；
- 标记区间、同向加成、逆势惩罚、下注占比、局连胜和天连胜信心结算；
- 多修正器应用、归一化和上下界；
- 固定种子结果复现；
- 下注上下限、余额不足和重复结算；
- 3D 筹码面额拆分、下注位置和输赢移交方向；
- 餐厅升级、周期收益、打烊、继续营业、典当和 Game Over；
- 午夜疲劳累积、跨午夜自然醒、固定睡到 08:00、睡眠不足和当天 08:00晕倒边界。

### 13.2 统计测试

使用大量模拟牌局检查：

- 无路势、无技能时的基础结果分布；
- 单一修正器的影响方向和幅度；
- 多修正器叠加后是否保持合法分布；
- 不同赌场和下注额度下的资金存活时间；
- 餐厅收益和典当是否产生可利用的无限资金策略。

统计测试不应要求每次运行得到完全相同的经验比例；固定种子回归测试与容差范围统计测试应分开。

### 13.3 端到端测试

至少覆盖：

1. 进入初级赌场，比较牌桌并完成下注结算。
2. 支付门票进入高级赌场，验证余额不足限制和下注上下限。
3. 旁观一局后路单和餐厅周期正常推进。
4. 路书标记在封盘前不预览信心，封盘后分项反馈与结算一致。
5. 搓牌回弹、越阈值揭牌和快速开牌。
6. 餐厅升级、周期发放和典当确认。
7. 餐厅打烊后暂停、继续营业至下次打烊、自宅两种休息和强制晕倒恢复。
8. 地图与自宅昼夜图片在 06:00/18:00 边界平滑切换。
9. 资产完全耗尽后进入 Game Over。

### 阶段一：规则与模拟

### 阶段三：3D 搓牌

- 纸牌模型、发牌和近景镜头；
- 鼠标抓角、弯曲、回弹和揭牌；
- 快速开牌；
- 音效、阴影和性能调优。

### 阶段四：验证与平衡

- 概率与经济模拟；
- 可用性测试；

## 15. 技术风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 玩家认为信心是暗箱操纵 | 不信任系统 | 封盘后显示每个加减项和最终触发率，提供内部精确调试数据 |
| 目标结果与真实牌靴冲突 | 规则不可信 | 所有结果通过百家乐规则生成，记录条件采样回退 |
| 后台定时器被浏览器节流 | 多桌不同步 | 使用时间戳和恢复时补算，不依赖定时器准点执行 |
| 搓牌变形不稳定 | 核心体验失败 | 不用通用软体物理，采用受约束的确定性网格变形 |
| 多路数叠加使信心长期封顶 | 策略坍塌 | 对叠加频率做统计测试，并保留全局上下界与数值配置 |
| 餐厅收益破坏风险循环 | 无限恢复资金 | 通过账本和经济模拟调整周期、收益与典当价值 |
| 路单在多桌大厅中难以阅读 | 择桌失去意义 | 使用共享格位模型、压缩大路和响应式固定格尺寸 |

## 16. 暂不采用的方案

- **Unity 作为 MVP 起点**：完整 3D 场景并非当前验证重点，Web 技术迭代更快。
- **全界面 Three.js**：路单和管理界面使用 DOM 更清晰、可访问且易调整。
- **完整软体物理**：增加不稳定性和调参成本，不能直接改善核心验证。
- **每桌独立高频循环**：后台桌只需逻辑推进，统一调度更易测试。
- **服务端架构**：MVP 为单机验证，不需要账号、联机和权威结算。

## 17. 完成标准

技术 MVP 达到以下条件时可进入集中玩法测试：

- 两座赌场和全部后台桌能稳定推进，切换页面不会丢局或重复结算；
- 标准百家乐规则、路单和基础路势通过自动测试；
- 固定随机种子能够完整复现一局的概率来源、结果和牌序；
- 玩家能完成餐厅到赌场再回到餐厅的完整资金循环；
- 关键牌搓牌在目标桌面设备稳定达到接近 60 FPS；
- 搓牌输入不会改变已冻结结果；
- 调试面板能够解释任意一局的概率变化和资金变化；
- Game Over 条件可靠且不存在明显重复收益或无限资金漏洞。
